實戰教學

如何把需求說明交付成任務

一句「手機畫面不友善，改善一下」＋一張截圖，AI 就能一次改對嗎？ 以 尋龍高手 DragonFinder 手機版修復 為實例，教你寫出 agent 能精準執行的任務交付文。

一、為什麼「直接改」常常改不好？

同一個需求，兩種交付方式，結果天差地別：

✕ 不好的交付

「手機開啟遊戲進入遊戲闖關，遊戲畫面不友善，進行改善」

問題：沒有專案路徑、沒有現象描述、沒有驗收標準。agent 只能到處猜： 是哪個專案？哪裡不友善？改到什麼程度算好？最後做出來的東西往往不是你想要的。

✓ 好的交付

附上截圖＋正確專案路徑＋六要素任務包（見第三節）。agent 照單施工， 驗證照表操課，一次到位。

需求 + 截圖→ AI 診斷根因→ 施工包（檔案/行號/改前改後）→ 驗證步驟→ 交付驗收

二、有效任務的六大要素

要素作用範例（來自本次實戰）
1. 專案定位讓 agent 直接進對資料夾，不用全機搜尋C:\MY_AI_JOBS\dragonfinder（遠端 hungmin368/df）
2. 問題現象描述「看得到的錯」，最好附截圖5 顆按鈕浮起蓋住棋盤第 3、4 列；🔊 被切半
3. 根因分析指出問題程式碼位置，agent 不必重新排查style.css:230 的 position:sticky 在手機視窗被拉起
4. 修改內容精確到「檔名＋行號＋改前改後」，零猜測230 行整行替換為三段；main.js 新增 fitMobileBoard()
5. 驗證方式定義「怎樣算改好」，這是驗收的依據390×844 直向 / 844×390 橫向跑 4×4 與 18×18，按鈕不遮盤
6. 交付約定遵守專案規範，別破壞既有流程依 agents.md：建 worklog、不動 *.bak、驗證過才 push

三、實戰拆解：DragonFinder 手機版修復

收到的原始需求

使用者傳了一張手機截圖，只說：「手機開啟遊戲進入遊戲闖關，遊戲畫面不友善，進行改善」。

第一步：補齊資訊，讓 AI 診斷

好的交付不等於你要自己會寫程式。你只要補三樣東西，剩下的診斷交給 AI：

  • 截圖：圈出/指出哪裡不對（這次是截圖本身就看得到按鈕壓在棋盤上）。
  • 專案路徑：C:\MY_AI_JOBS\dragonfinder（路徑錯了，後面全白搭）。
  • 重現步驟：「手機直向 → 進 4×4 關卡 → 畫面就如截圖」。

第二步：把診斷轉成施工包

AI 診斷出根因後，請它產出「可直接施工」的內容。本次的根因與修法：

根因：按鈕列用了 position:sticky; bottom:calc(var(--dlgh,118px)+18px)， 本意是讓按鈕浮在伴伴列上方；但手機視窗矮，sticky 把按鈕整塊拉起，壓住棋盤。 加上 5 顆按鈕換行成 2~3 排、棋盤寬度沒扣除周圍 UI，整頁超高 → scroll + sticky = 災難。

修法：sticky 只在桌機生效；手機改成「單排按鈕回到文件流」＋「JS 量測可用高度、動態縮放棋盤」。

▶ 點開看本次任務包的實際樣貌（精簡版） 
【專案】C:\MY_AI_JOBS\dragonfinder（遠端 hungmin368/df，branch main）
【現象】手機直向：5 鈕蓋住棋盤 3、4 列；狀態列被遮；header 🔊 切邊
【根因】style.css:230 #controls sticky；按鈕換行；棋盤未扣周圍 UI 高度
【修改】
1. style.css 第 230 行 → 改為預設不 sticky，桌機媒體查詢才 sticky
2. style.css 檔尾 → 新增 @media (max-width:720px) 區塊（緊湊 header、單排鈕、--boardw 棋盤）
3. main.js → 新增 fitMobileBoard()，掛在 ResizeObserver / renderBoard / resize 三處
4. index.html → 4 處 ?v=1.9.3 改 v=1.9.4
【驗證】390×844 直向、844×390 橫向：4×4 與 18×18 一屏可見、鈕不遮盤；
         桌面 1280×800 行為不變；python3 -m http.server + curl 全 200
【約定】依 agents.md：建 worklog、不動 *.bak、驗證過才 commit+push

四、萬用交付模板（複製即用）

把【】中的內容換成你的，貼給任何可寫 agent 即可 
任務：【一句話說明要改什麼】

【專案】
路徑：【本機絕對路徑】
（若已知）遠端倉庫 / branch / 部署位置：【】
（若該專案有 agent 規範檔）遵守：【例如 agents.md 的規定】

【問題現象】
裝置 / 環境：【手機型號或 viewport 尺寸、瀏覽器】
重現步驟：【點哪裡、進哪個頁面，錯誤就出現】
實際結果：【看到了什麼，附截圖】
預期結果：【應該長什麼樣】

【根因】（若已知，可留給 AI 診斷）
檔案：行號 → 問題程式碼 → 為什麼造成現象

【修改內容】
- 檔案 A：第 N 行【改前 → 改後 / 或貼完整程式碼】
- 檔案 B：新增函式【完整程式碼】、掛載位置【】
（原則：精確到行號與完整程式碼，agent 不需要做任何設計決策）

【驗證方式】（沒過就不算完成）
1. 啟動方式：【例如 python3 -m http.server】
2. 檢查點：【viewport 尺寸、要測的功能路徑、預期畫面】
3. 迴歸檢查：【哪些既有行為必須維持不變】

【交付約定】
- 不動哪些檔案：【例如 *.bak】
- 要不要 worklog / 文件：【】
- 何時才能 commit/push：【驗證通過後】

五、交付前檢查清單

  • 專案路徑是「絕對路徑」，而且親自確認過存在（不是印象中的路徑）？
  • 有截圖或具體描述「錯的樣子」，並說明怎麼重現？
  • 有寫「預期應該長什麼樣」嗎？（沒有標準，驗收就會吵架）
  • 修改內容精確到「檔名＋位置＋完整程式碼」，agent 不用猜？
  • 列出「一定要維持不變」的既有行為（防 agent 改過頭）？
  • 驗證方式具體可執行（viewport 尺寸、操作步驟、通過條件）？
  • 交代專案特殊規範（.bak 不能動、要建 worklog、文字語言）？
  • 環境限制說清楚了嗎？（例如：此 session 無寫入工具，請建立任務派發）

六、本次案例給你的最大啟示

✓ 重點整理
  1. 你不需要會寫程式，但你需要會「描述現象、給對路徑、定義驗收」。
  2. 截圖是最高效的溝通——這次一張圖就讓根因（按鈕壓棋盤）無從抵賴。
  3. 先讓 AI 診斷、再讓它出施工包，兩段式進行，比一步到位更準。
  4. 驗證條件寫得越具體（尺寸、關卡、步驟），交出來的東西越不用退件。
  5. 遇到「agent 說不能做」，先確認是工具權限問題還是需求不清楚——這次是前者，解法就是把施工包轉交給有權限的執行者。
