🐉 DragonFinder（尋龍高手）多語模式工程評估

評估日期：2026-09-28　·　評估版本：v1.9.10（index.html 主線）　·　性質：純評估，未修改任何程式碼　·　範圍：英文模式＋三語（繁中／簡中／英文）漸進架構
結論摘要

本遊戲可以以合理的成本支援英文模式，總工作量估計 7.5～10 個人日。 工程上沒有技術障礙：專案零依賴、無框架，採用「自製輕量字典 + data-i18n 標記」即可，不需引入任何外部 i18n 函式庫。 真正的成本集中在兩件事：

  • 字串抽取：約 250～300 個動態字串散落在 js/main.js（456 行含中文）的字串拼接中，抽取工作機械但量大、需完整回歸。
  • 內容翻譯：16 章故事約 4,000+ 字的敘事文本、約 100 句伴伴對話、140 隻恐龍命名，是需要品質把關的內容工程。

另外有 8 個需要決策的議題（恐龍命名策略、故事翻譯品質、切換方式、Logo 素材、字型涵蓋、AGENTS.md 規則修訂、首次偵測預設方向、簡中字型），詳見決策點。

延伸評估（同日追加）：可採「三語漸進架構」——前期先建語言無關骨架（約 4.5～6 人日，繁中全量可用、含首次啟動語言偵測），簡中與英文於開發後期逐批補建（三語合計約 9.5～13 人日）。

二、技術特性（決定工程做法）

有利因素（降低工程風險）
  • 零依賴、無框架：三個 plain <script>＋全域變數。自製 t(key) 字典函式即可，不必引入 i18next 等函式庫，符合專案精神。
  • 存檔無語言耦合：17 個 dinodoku-* localStorage 鍵全存 ID／數字／布林，無任何中文內容 → 切換語言不影響玩家存檔，不需遷移。
  • 題庫與美術免處理：2000 關 tower 題目、19 張故事場景 SVG、CSS 皆無文字內容。
  • 地圖文字是動態的：區域標籤由 regionLabel() 即時組合（emoji＋名＋N×N），不是燒在地圖圖片上。
  • 名稱顯示單點收斂：所有恐龍名都讀 name 欄位 → 資料加一個 name_en 欄位、一個取值函式即可全覆蓋。
  • 時間格式語言中性：fmtSec() 輸出 6:00 形式，無需處理。
不利因素（主要成本來源）
  • 字串散落且內嵌於 HTML 拼接：main.js 有 49 處 innerHTML、72 處 textContent，中文字串直接寫在拼接模板裡（如 '🗺️ <b>出沒區域：</b>'+…），抽取時要逐處改寫為 key，且部分句子含 HTML 標籤與變數。
  • 內嵌字型是子集化的：Huninn／Iansui 僅涵蓋現有字元。新增任何新字串（中英文皆然）都可能缺字；英文模式需確認 Latin 涵蓋範圍，必要時重新子集化（需原字型與子集工具流程）。
  • 英文比中文長：按鈕（「清除」「提示」）、HUD（「第 N 局」「分數」）、地圖區域標籤（錨點座標固定）、對話框等固定尺寸元素可能溢出，需逐項排版回歸。
  • 6 處系統對話框（confirm/alert）也是玩家可見文字。
  • 單檔打包：build_single_file.mjs 以逐檔 replace 內嵌，新增字典檔必須同步調整打包腳本與 index.html 的 script 標籤。
  • 治理規則：AGENTS.md 明訂「玩家可見 UI 文字保持繁體中文」，新增英文模式需同步修訂此規則。

五、三語漸進架構方案（繁中先行、簡中／英文後期建構）

結論：可行，且建議採用

「前期把骨架設計成語言無關、開發後期再一次補建簡中與英文」不僅可行，還比「先做雙語再擴充」更省：骨架只建一次，之後加語言＝填字典＋一輪回歸，不再改程式碼。前期投入＝Phase 1＋2（約 4.5～6 人日）即可交付「繁中全量、骨架三語就緒」的版本，簡中、英文何時補、補哪個，由發布計畫決定。

5.1 骨架設計（前期一次到位）

  • 三份對稱字典＋fallback 鏈：字典以語言碼為鍵（zh-Hant／zh-Hans／en），t(key) 依「當前語言 → zh-Hant」退回。任何語言缺 key 都退回繁中，做到骨架先上、字典後補、隨時可出貨。
  • 恐龍名同構：data.js 名稱欄位一次改為 name_zh_Hant／name_zh_Hans／name_en，讀取函式（如 nameOf(id)）一次寫好；後期加語言只補欄位值。
  • 首次啟動語言偵測：以 navigator.language（瀏覽器 UI 語言）為偵測來源；不用 IP 地理位置偵測——那需要外部 API，違反本專案零依賴、完全離線原則，且瀏覽器語言本來就是玩家自設偏好，比 IP 更準。僅在 dinodoku-lang 鍵不存在時偵測一次並存檔，之後以手動切換為準，自動偵測不覆蓋玩家偏好：
const saved = localStorage.getItem('dinodoku-lang');
const s = (navigator.language || '').toLowerCase();
let lang = 'en';                                    /* 預設英文（方向可依客群反轉，見 D7） */
if (s.startsWith('zh')) lang = /cn|sg|hans/.test(s) ? 'zh-Hans' : 'zh-Hant';
if (!saved) { try { localStorage.setItem('dinodoku-lang', lang); } catch(e){} }
  • 切換機制：選單 🌐 鈕（繁／簡／EN 三選一）寫入偏好後 location.reload()，三語共用同一套機制。
  • 已知邊界：瀏覽器設成英文但偏好中文的海外玩家會被誤判 → 手動切換鈕（W2）仍是必要入口，自動偵測只決定初始預設。

六、結論

英文模式對 DragonFinder 是可行且邊界清楚的工程：架構一天可立起來，難度不在技術而在字串抽取的完整度與敘事內容的翻譯品質。估算總量 7.5～10 人日，分四個可獨立驗收的階段推進；其中 Phase 1＋2（約 4～5.5 人日）完成後即可交付「UI 完整雙語、內容暫緩」的可用版本，故事與對話的翻譯可以之後逐批補上，不阻塞上架。

唯一建議先做的前置動作：先做字型 Latin 涵蓋驗證（半天內可確認），因為它是唯一可能在期中才爆出的技術風險；其餘項目風險皆可控。

若採三語漸進架構（第五節）：前期 4.5～6 人日建立語言無關骨架（含首次啟動語言偵測，繁中全量可用），簡中與英文後期逐批補建，三語合計約 9.5～13 人日；各語言可獨立出貨、互不阻塞，且骨架完成後加語言不再需要改程式碼。
