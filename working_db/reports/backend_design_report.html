零、結論摘要（先看這裡）

為什麼要做目前遊戲 100% 離線，分數、圖鑑、資源全存在瀏覽器 localStorage；開 F12 改一行數字、或使用內建「工程模式」就能任意加資源與過關——單機自娛沒問題，但一旦有排行榜或付費，這些都必須由伺服器說了算。
分數怎麼驗本遊戲分數＝過關時剩餘秒數、上限恆為 30×N 秒（N×30 的沙漏總量），且遊戲盤面是「唯一解」——這兩個性質讓驗證變得可行：伺服器握有盤面答案＋事件紀錄比對，即可否決絕大多數造假。詳見第三章。
內購怎麼做上架商店賣數位商品必須走 Apple／Google 內購（平台政策），且收據驗證一定要在伺服器做（前端驗證可被繞過、金鑰不可放前端）。流程：App 購買 → 收據送自家後端 → 後端向 Apple／Google 驗證 → 入帳到雲端錢包。詳見第四章。
建議順序Phase 1 匿名帳號＋雲端分數驗證 → Phase 2 內購驗證與雲端錢包 → Phase 3 排行榜與強化防作弊。後端沿用先前調研首選 Supabase（免費層、不綁卡），備選 Cloudflare Workers＋D1。
2026-10-14 追加第十一章回答「離線可玩＋留言需連線是否可行、如何收費」：可行。單機核心（含 8×8 以上與龍塔）永久離線免費；攻略留言在玩家主動開啟時才提示連線（非阻斷式提示卡＋離線快取可讀）；留言免費，錢只收在「完整版解鎖」一次買斷。含連線偵測 UI 流程、留言表 DDL、UGC 合規清單與防繞過界線。
重點原則：維持「離線也能玩」的體驗——單機遊玩、離線局不經雲端（分數只留本機，不進排行榜）；要上雲端的分數與付費資源，一律走伺服器驗證後才算數（server-authoritative）。

1.2 作弊面（現行狀態下任何人都能做到的事）

改 localStorage：在瀏覽器主控台執行 localStorage.setItem('dinodoku-lv', '{"13":{"best":390,"total":999999}}') 即可把個人總分改成任意數字——總分顯示邏輯（lvTotal()）對存檔內容沒有任何校驗。
改記憶體／呼叫函式：主控台可直接執行遊戲內部函式（如資源加值、強制過關），也能直接改 ECON.seeds 等變數後存檔。
工程模式：正式版頁面仍包含 dev-win（立即過關）、dev-seeds（種子+100）等按鈕；即使入口隱藏，程式碼在瀏覽器端就能被觸發。上架／上線前應在發佈建置中整個剝除。
誠實的界線：休閒單機遊戲「自己改自己的存檔騙自己」通常無害；真正需要後端把關的是三件事——(1) 一旦有跨玩家排行榜或雲端存檔，分數的公信力；(2) 一旦收費，付費與發放的完整性；(3) 上架商店時平台對「數位商品必須經商店內購＋伺服器驗證」的要求。

1.3 讓驗證可行的兩個遊戲特性

特性 A：分數有數學上限。沙漏總量 TIMER.total = N×30，剩餘時間永遠 ≤ 總量（+30 秒回填也不能超過初始值，js/main.js:1377）。因此每一局分數必然落在 [0, 30×N]：6×6 最多 180 分、13×13 最多 390 分、18×18 最多 540 分。任何超出上限的分數不必驗證，直接拒絕。
特性 B：盤面唯一解且「揭示即證明」。遊戲要求每行／每列／每色區恰 1 個隱藏物（index.html:138-144），生成器會重試到唯一解（js/main.js:178-255）。玩家只能靠逐格點擊揭示來過關，也就是說——一場合法的勝利，必然在事件紀錄中點中了全部 N 個正確位置。只要伺服器自己握有盤面答案，就能對事件紀錄做硬性驗證（見第三章）。
注意：盤面生成器（randomRegions／solve2／generatePuzzle）是純 JS、無 DOM 依賴的函式，可直接移植到伺服器端（Deno／Node 皆可）執行，這是後端能「自己產盤面、自己存答案」的關鍵。

二、設計目標與整體架構

2.1 設計目標

  • 保留離線可玩：沒有網路時遊戲與現在完全一樣（本機分數、本機存檔）；雲端只是「加值層」。
  • 伺服器權威（server-authoritative）：要進雲端的分數、要花錢買的資源，由伺服器驗證與記帳後才生效。
  • 最小侵入：不重寫遊戲；前端只加「開局取盤面、事件記錄、結果提交」三個掛點＋一個 API 客戶端。
  • 誠實標示：離線局與無法線上驗證的局標記為「本機限定」，不進排行榜、不參與雲端計分。
  • 零依賴精神：前端僅用 fetch；後端用免費層服務，不新增 npm 依賴鏈。

2.3 身分模型：匿名裝置帳號

現有遊戲沒有帳號。為了把「雲端分數」與「購買紀錄」綁在一個可持續的身分上，建議最小可行的方案：

1
首次上線時註冊匿名帳號
App 產生一組隨機 player_token（32 bytes），向 POST /v1/auth/device 換取正式的 player_id 與權杖；權杖只存裝置端（localStorage dinodoku-player），伺服器端只存雜湊。不用 email、不用密碼，符合休閒遊戲體驗。
2
轉移碼（建議加值）
遊戲內「設定」顯示一組一次性轉移碼，玩家換裝置時輸入即可把雲端資料（含購買紀錄）帶過去。成本低、能擋掉最常見的「換手機＝付費紀錄全消失」客訴。
3
（後續可選）正式登入
未來需要跨裝置同步或社群功能時，再疊加「Sign in with Apple／Google」把手機帳號升級成正式帳號，不影響既有匿名玩家。列為 Phase 3 之後。
為什麼不能不做？消耗型內購（如種子包）一旦購買、發放、消耗，就不像「非消耗型」那樣可以靠商店的「恢復購買」重建。沒有帳號綁定，玩家清除瀏覽器資料／換裝置後付費紀錄無從恢復，幾乎必然產生退款糾紛——因此帳號（哪怕是匿名的）是內購的前置條件。

3.2 三層防護模型（可以做到什麼、做不到什麼）

防作弊沒有「一步到位」，只有低成本到高成本的疊加。建議依下表逐層加，並誠實理解每層的極限：

層級做法能擋住的作弊擋不住的作弊成本
L1 邊界與速率 結算時提交 (N, score, 用時)；伺服器只做 V1–V3＋速率限制（例如每 30 秒最多 1 局、單日上限）＋統計異常標記（例如平均每抓 < 0.25 秒） 改 localStorage 直接刷天文數字的分數；超上限分數；腳本化分鐘刷數百局 「宣稱很快通關」（例如實際玩 3 分鐘、宣稱 40 秒） 極低（1 個函式）
L2 伺服器盤面＋事件驗證 開局由伺服器發盤（伺服器保存答案）；結算提交完整操作事件流；伺服器重演「點擊→揭示」序列，比對答案 上一層全部＋「點錯當命中」、「偷加捕捉器次數」、「沒點完就宣告過關」；盤面被改（答案在伺服器手上） 完全偽造時間軸（宣稱暫停時長、宣稱的單步反應速度）；外掛預知答案後快速點擊（仍受 V2 上限與統計標記約束） 中（Edge Function＋事件格式＋前端記錄器）
L3 即時串流 遊玩中每 2 秒心跳（含當前剩餘時間）；伺服器用自己的時鐘重建時間軸；關鍵事件即時回報 L2 全部＋「存檔後補交」「遠端游離改時間」（時間軸由伺服器記） 真人代打、以人類速度運行的腳本；手機端記憶體修改後即時送出合法操作（此時只能靠統計與人工複核） 較高（連線品質要求、前端改動多）
建議：休閒解謎遊戲的分數動機有限，L1＋L2 已足以支撐一個可信的排行榜；L3 不需要一開始就做。真正要「零容忍」的其實是內購（第四章），那裡的驗證是商店官方 API 級別的硬驗證。

3.3 開局與結算流程（線上局）

1
開局　前端 POST /v1/runs（附 N）→ 伺服器從該尺寸的盤面庫挑一張（盤面庫＝伺服器持有的 regionOf＋隱藏物位置），生成 runId 並回傳盤面資料與 startedAt（伺服器時間）。
盤面庫可直接匯入現有 POOL_DATA（10～13 尺寸）＋伺服器端用移植的 generatePuzzle 預先產好 6～9／14～18 的存貨；旋轉／鏡像（現有 transformBoard 的 8 種變換）在結算時由選手申報，伺服器換算答案。
2
遊玩　與現在完全相同（即時、無等待）。前端記錄事件流：每次 reveal（揭示某格、命中或落空）、mark（✕ 標記）、hint（用提示）、skip 等，各帶一個「活動時間戳」（沿用沙漏的暫停邏輯：暫停期間不計）。事件存在記憶體，結算才一次上傳——不影響遊玩效能。
3
結算　前端 POST /v1/runs/{id}/finish（附事件流、宣稱分數、變換參數）→ 伺服器（Edge Function）：驗證 V1–V8 → 用答案重演事件流 → 計算伺服器認可分數 → 寫入 runs 與 scores（僅當認可分數 ≥ 目前最佳或累積更新）→ 回傳新的區域戰績與個人總分。同一個 runId 只接受一次結算（冪等：重送回傳相同結果，不重複計分）。
4
顯示　結算畫面顯示的分數改以「伺服器回傳值」為準；本地 LV 僅作為離線快取與顯示加速，連線時以雲端覆寫。衝突原則：server wins（只針對雲端局；離線局維持本機）。

    {"t": 5100,  "a": "mark",   "c": 9},
    {"t": 7400,  "a": "reveal", "c": 21, "hit": "miss"},  // 落空：伺服器確認 c 不是答案格
    {"t": 9600,  "a": "hint",   "c": 33},
    {"t": 12400, "a": "reveal", "c": 33, "hit": "chest"}
    // …直到第 N 個命中（過關）
  ]
}

伺服器驗證步驟：

  1. 事件時間單調遞增、格式合法、數量上限（例如 ≤ 4×N×N，防灌爆）。
  2. 每個 reveal：該格必須「尚未被揭示」且未超過 N+3 次；hit 與伺服器答案一致（transform 換算後）；hit=miss 時該格必須不是答案格。
  3. 過關條件：事件流中命中數恰為 N，且最後一筆後無異常事件。
  4. 分數：serverScore = clamp(30N − activeMs/1000, 0, 30N)（取整規則與前端 Math.floor 對齊），與 claimedScore 差距 ≤ 1 秒才認可，否則以 serverScore 為準並記警告。
  5. 統計標記：平均每步操作 < 250ms、連續局數異常、同盤面重複秒殺 → 標記進審核佇列（不直接封鎖，先觀察）。

4.2 平台整合現況（2026-10 查證）

iOS（Apple）

  • 購買端：StoreKit 2；購買成功後拿到交易 JWS（signed transaction）。
  • 伺服器驗證：App Store Server API——以後端向 GET /inApps/v1/transactions/{transactionId} 查驗交易狀態，或直接驗簽前端傳來的 JWS。金鑰為 In-App Purchase Key（.p8）＋ Issuer ID ＋ Key ID，只存後端。
  • 事件通知：App Store Server Notifications V2（webhook，JWS 簽章鏈可對 Apple Root CA 驗證）——處理退款（REFUND）、撤銷等事後狀態變化。
  • 消耗型商品：結算畫面需呼叫 Transaction.finish()（由前端在後端確認入帳後執行）。
  • 測試：StoreKit Testing（本地）＋ App Store Sandbox 帳號。

Android（Google）

  • 購買端：Google Play Billing Library（0.1 節查證：2026-06 最新為 9.1.0；2026-08-31 起新上架／更新必須使用 8.0 以上，必要時可申請延長至 2026-11-01）。
  • 伺服器驗證：Google Play Developer API（androidpublisher）——以 purchaseToken 查詢購買狀態（一次性商品 purchases.products.get；新式 API 以官方現行文件為準）。
  • 事件通知：RTDN（Real-time Developer Notifications，經 Google Cloud Pub/Sub）——一次性商品事件 ONE_TIME_PRODUCT_PURCHASED／ONE_TIME_PRODUCT_CANCELED，退款走 VoidedPurchaseNotification；訊息含 purchaseToken 與 sku，收到後仍需呼叫 Developer API 取完整狀態。
  • 消耗型商品：入帳後需「消耗」該筆購買（伺服器端呼叫 consume，或由 App 端 consumeAsync），否則同帳號無法再次購買同一商品。這是 Android 特有的必做步驟。
  • 測試：Play Console 授權測試帳號（License testers）＋ 內部測試軌道。

4.3 購買與發放流程

1
App 端發起購買（StoreKit 2／Play Billing）→ 玩家以商店帳號完成付款。
2
App 把交易憑證送自家後端：iOS＝交易 JWS／transactionId；Android＝purchaseToken＋productId＋orderId。前端只負責轉交，不做任何「是否已付款」的判斷。
3
後端（Edge Function iap-verify）向商店驗證：Apple App Store Server API／Google Developer API。檢查：簽章有效、productId 在白名單、交易狀態已付款、綁定的 App 正確、未被撤銷。
4
冪等入帳：以 (platform, transaction_id) 唯一鍵寫入 iap_transactions；同一筆交易重複送達→回傳「已處理」，不重複發放。發放寫入錢包 wallet 並記一筆 ledger（+🌌×120, reason=iap）。
5
告知 App 更新餘額：回傳最新錢包；App 更新顯示。（Android）伺服器端完成消耗；（iOS）App 端 Transaction.finish()。
6
事後事件（非同步）：Apple Notifications V2／Google RTDN 進入對應 webhook → 退款／撤銷時更新 iap_transactions.status，並依政策處理資源（見 4.5）。

4.5 退款、撤銷與異常處理政策（先定好，避免爭議）

  • 退款（Apple REFUND／Google VoidedPurchase）：webhook 到達→標記交易為 refunded→ledger 記一筆負值。資源扣減策略建議：先扣未使用部分至 0；若已消耗完畢，餘額記為 0 並標記帳號（不主動追討、不封鎖——休閒遊戲以符合商店規範為底線，避免客訴升級）。
  • 重複送達／競態：(platform, transaction_id) 唯一鍵＋交易內加鎖，保證恰好發放一次（exactly-once）。
  • 待處理購買（pending）：兩平台都有延遲付款情境，收到時回「處理中」，待 webhook 確認後才發放。
  • 沙盒交易：驗證環境與正式環境分流（Apple sandboxReceipt／Google test purchase），沙盒交易僅入測試玩家帳號。

-- 玩家（匿名裝置帳號）
create table players (
  id                 uuid primary key default gen_random_uuid(),
  device_secret_hash text not null,          -- 只存雜湊
  created_at         timestamptz not null default now(),
  flagged            boolean not null default false   -- 統計異常標記
);

-- 盤面庫（伺服器持有的答案；匯入現有 POOL_DATA＋伺服器端預生成）
create table boards (
  id        bigint generated always as identity primary key,
  n         smallint not null check (n between 6 and 18),
  layout    jsonb    not null,   -- regionOf（N*N）
  cats      jsonb    not null,   -- 隱藏物位置（N 個）
  created_at timestamptz not null default now()
);
create index idx_boards_n on boards (n);

-- 每局
create table runs (
  id          uuid primary key default gen_random_uuid(),
  player_id   uuid not null references players(id),
  board_id    bigint not null references boards(id),
  n           smallint not null,
  transform   smallint,                       -- 0..7，結算時填入
  status      text not null default 'open'    -- open / finished / rejected / expired
              check (status in ('open','finished','rejected','expired')),
  started_at  timestamptz not null default now(),
  expires_at  timestamptz not null,           -- 例：started_at + 6 小時
  claimed_score int,
  verified_score int,
  result      jsonb                           -- 驗證明細（命中序列、警告）
);

-- 事件（可選：完整留存供複核；也可只留在 result）
create table run_events (
  run_id  uuid not null references runs(id) on delete cascade,
  seq     int  not null,
  t_ms    bigint not null,
  action  text not null,
  cell    int,
  primary key (run_id, seq)
);

-- 雲端戰績（對應現有 LV[n].best / total）
create table scores (
  player_id uuid not null references players(id),
  n         smallint not null,
  best      int not null default 0 check (best  >= 0),
  total     int not null default 0 check (total >= 0),
  updated_at timestamptz not null default now(),
  primary key (player_id, n)
);

-- 錢包（對應 ECON 的可付費資源）
create table wallet (
  player_id uuid primary key references players(id),
  seeds     int not null default 0 check (seeds   >= 0),
  tickets   int not null default 0 check (tickets >= 0),
  potions   int not null default 0 check (potions >= 0),
  updated_at timestamptz not null default now()
);

-- 流水帳（每一筆增減都要有來源）
create table ledger (
  id         bigint generated always as identity primary key,
  player_id  uuid not null references players(id),
  currency   text not null check (currency in ('seeds','tickets','potions')),
  delta      int  not null,
  reason     text not null,           -- iap / refund / chest / reward / spend / adjust
  ref        text,                    -- runId 或 transaction_id
  created_at timestamptz not null default now()
);
create index idx_ledger_player on ledger (player_id, created_at desc);

-- 內購交易（冪等的核心）
create table iap_transactions (
  id             bigint generated always as identity primary key,
  player_id      uuid not null references players(id),
  platform       text not null check (platform in ('apple','google')),
  transaction_id text not null,       -- Apple transactionId／Google purchaseToken
  product_id     text not null,
  status         text not null default 'verified'
                 check (status in ('verified','pending','refunded','revoked')),
  raw            jsonb not null,      -- 商店原始回應（稽核用）
  created_at     timestamptz not null default now(),
  updated_at     timestamptz not null default now(),
  unique (platform, transaction_id)
);

-- 商店通知稽核
create table iap_notifications (
  id           bigint generated always as identity primary key,
  platform     text not null,
  message_id   text not null,
  payload      jsonb not null,
  result       text,
  received_at  timestamptz not null default now(),
  unique (platform, message_id)
);

十一、離線核心＋連線留言：混合模式規格（2026-10-14 追加）

這一章回答什麼：提問「如果做成離線可玩，當要開啟攻略留言功能就會提醒玩家要連線，這樣可行嗎？那這樣要如何收費」。答案：可行，而且是這個產品最務實的切法——單機核心永久離線免費，留言等 UGC 功能在玩家主動開啟時才提示連線，收費只賣「完整版解鎖」（非消耗型一次買斷），留言功能本身不收費。以下為可直接動工的規格。

11.1 功能分層與網路需求

功能離線需連線依據／說明
盤面挑戰 4×4–12×12（九大區域）可—盤面由客戶端 newBoard() 即時生成（js/main.js:1005），區域表 REGION_META（js/main.js:393-396）；全程零網路請求
圖鑑／資源／存檔可—localStorage dinodoku-*
龍塔挑戰（2000 關）可—js/tower.js 預生成關卡
攻略彈幕（飛字播放）讀快取取新留言離線時播放最近快取；無快取則顯示「尚無留言」而非錯誤
攻略留言板（閱讀）讀快取取新留言見 11.3 快取規格；狀態條須標示「離線快取 · 同步於 X」
攻略留言板（發表／按讚）不可是UGC 必須經伺服器過濾與留存（合規要求，見 11.5）

11.2 連線偵測與提醒 UI 流程

1
點「📋 留言板」→ 先秒開快取
立刻讀 dinodoku-twcache-<level> 渲染，狀態條顯示灰色「離線快取」。玩家不會看到空白或轉圈等網路。
2
背景探測連線（不阻擋畫面）
navigator.onLine === false → 直接判定離線；為 true 仍可能是無效連線（captive portal），故再發 GET /v1/comments?level=n&limit=20，逾時 4 秒。
3
成功 → 靜默同步
用伺服器資料取代快取、寫回快取與同步時間、狀態條轉綠「已同步 · 剛剛」、解鎖「發表／按讚／檢舉」。
4
失敗 → 提示卡（非阻斷式）
顯示置中提示卡：「攻略留言需要網路連線」＋說明「你可以離線繼續玩，連線後即可閱讀與發表攻略」。按鈕：重試、返回遊戲；若本關有快取則多一顆 閱讀離線快取。不使用蓋滿整頁的 modal，不鎖住返回鍵。
5
離線按「送出」→ 不丟字
保留暱稱與內容於輸入框，提示「需要網路才能發表，已幫你保留內容」，並在 dinodoku-twdraft-<level> 存草稿；恢復連線後可一鍵送出（不自動送出，避免玩家沒注意就發表）。
6
online／offline 事件自動處理
監聽 window.online：留言板開著就自動重試一次並更新狀態條；遊戲中不主動跳窗打斷遊玩。
7
鐵律
離線永不阻擋任何單機功能（含 8×8 以上與龍塔）；連線提示只出現在玩家主動要求 UGC／雲端功能時。這是「離線可玩」承諾的底線，也是商店評論的保護傘。
文案建議（繁中、兒童友善）：「攻略留言需要網路連線 🌐
單機玩法不用網路，隨時都能玩！連線後就可以看到其他玩家的攻略、發表你的發現。」— 避免「錯誤」「失敗」等字眼。

11.3 離線快取規格

項目規格
快取鍵dinodoku-twcache-<level>（留言陣列）、dinodoku-twcache-meta-<level>（{syncedAt,count}）、dinodoku-twdraft-<level>（離線草稿）
每關快取筆數20 則（最新 10 ＋ 最高讚 10，去重）
有效期72 小時；過期仍可讀，狀態條改標「快取已過期 · 連線可更新」
容量控管只保留最近 30 關，其餘以 LRU 淘汰（30 字留言極省空間，遠低於 localStorage 約 5MB 上限）
寫入時機每次成功 GET /v1/comments 後；失敗不覆寫既有快取
相容既有本地版現有 dinodoku-twcomments-<level>／-twposted-／-twlikes- 保留為離線降級資料來源；首次連線後遷移為「我的發言紀錄」，避免玩家既有留言消失（遷移需寫入 js/main.js 的初始化與開發者重設清單）
隱私快取含其他玩家暱稱與留言 → 屬於「使用者產生內容」，須在隱私政策與商店申報中揭露

11.4 留言後端 Schema（Postgres／Supabase DDL）

-- 攻略留言（龍塔每關；規則沿用前端：每關限 1 則、留言 ≤30 字、暱稱 ≤12 字）
create table tower_comments (
  id           bigint generated always as identity primary key,
  level        smallint not null check (level between 1 and 2000),
  player_id    uuid not null references players(id),
  name         text not null default '' check (char_length(name) <= 12),
  body         text not null check (char_length(body) between 1 and 30),
  status       text not null default 'pending'
               check (status in ('pending','approved','rejected','removed')),
  like_count   int not null default 0 check (like_count >= 0),
  report_count int not null default 0 check (report_count >= 0),
  ip_hash      text,                              -- 只存雜湊，供灌水偵測
  created_at   timestamptz not null default now(),
  moderated_at timestamptz
);
create index idx_comments_level on tower_comments (level, status, like_count desc, created_at desc);
-- 每玩家每關只能留 1 則（與前端 dinodoku-twposted-<level> 一致）
create unique index uq_comments_player_level on tower_comments (player_id, level)
  where status <> 'removed';

-- 按讚（每玩家每關上限 3 個，於 Edge Function 計數檢查）
create table comment_likes (
  comment_id bigint not null references tower_comments(id) on delete cascade,
  player_id  uuid   not null references players(id),
  level      smallint not null,
  created_at timestamptz not null default now(),
  primary key (comment_id, player_id)
);
create index idx_likes_player_level on comment_likes (player_id, level);

-- 檢舉（UGC 合規必備）
create table comment_reports (
  comment_id bigint not null references tower_comments(id) on delete cascade,
  player_id  uuid   not null references players(id),
  reason     text   not null check (char_length(reason) <= 200),
  handled    boolean not null default false,
  created_at timestamptz not null default now(),
  primary key (comment_id, player_id)
);

-- 敏感詞庫（把前端 BAD 清單升級為伺服器端可熱更新的詞庫）
create table banned_words (
  word       text primary key,
  severity   smallint not null default 1 check (severity in (1,2)),  -- 1=直接擋下 2=轉人工審核
  updated_at timestamptz not null default now()
);

-- 玩家禁言旗標（加在既有 players 表）
alter table players add column muted boolean not null default false,
                    add column muted_until timestamptz;

-- 每日配額（每日 10 則，與前端 DAILY 一致；伺服器計數才算數）
create table comment_quota (
  player_id  uuid not null references players(id),
  day        date not null default (now() at time zone 'Asia/Taipei')::date,
  used       smallint not null default 0 check (used between 0 and 10),
  primary key (player_id, day)
);

對應 API（沿用第五章風格）

Method路徑用途身分離線行為
GET/v1/comments?level=n&limit=20取該關已核准留言（按讚數＋時間排序）公開（anon key）讀快取＋提示卡
POST/v1/comments發表留言（伺服器過濾＋配額＋冪等）Bearer 權杖存草稿，不送出
POST/v1/comments/{id}/like按讚／收回（每關上限 3）Bearer 權杖按鈕停用＋提示
POST/v1/comments/{id}/report檢舉Bearer 權杖按鈕停用＋提示
POST/v1/moderation/{id}審核：核准／下架／禁言（內部）service role—
權限原則（RLS）：前端只能讀取 status='approved' 的留言；tower_comments／comment_likes／comment_quota 的寫入一律只允許 Edge Function（service role）。玩家無法用 anon key 直接插入留言、洗讚或改配額。

11.7 防繞過界線（誠實說）

本地繞過無法阻止：盤面由客戶端 newBoard() 生成（js/main.js:1005）、龍塔關卡由 js/tower.js 預生成，8×8 以上的內容本來就在玩家手上的 JS 裡。改一行 HTML／JS 或用 DevTools 就能在本地解鎖，伺服器完全沒有參與環節、也無從否決。這在單機離線遊戲是結構性的，不是實作疏失。

四、建議方案細部設計（Supabase）

4.1 資料表結構

create table tower_comments (
  id         bigint generated always as identity primary key,
  level      int    not null check (level between 1 and 2000),
  name       text   not null check (char_length(btrim(name)) between 1 and 12),
  text       text   not null check (char_length(btrim(text)) between 1 and 200),
  created_at timestamptz not null default now(),
  likes      int    not null default 0,
  reports    int    not null default 0
);
create index idx_tc_level on tower_comments (level, likes desc, created_at desc);

單表即可；2000 關以索引查詢毫無壓力。留言量極大時（數萬則以上）再考慮分頁（Range header）。

4.2 安全規則（Row Level Security）

alter table tower_comments enable row level security;

create policy "任何人可讀"  on tower_comments for select using (true);
create policy "任何人可新增（受限欄位）" on tower_comments for insert
  with check (likes = 0 and reports = 0);
-- 故意「不」建立 update／delete 政策：匿名金鑰無法改刪任何留言

誠實的限制：Supabase 的 anon 金鑰會出現在前端原始碼，這是公開常數而非機密；RLS 能保證的是「只能新增合法長度的資料、不能改刪」，防灌水主要仍靠前端冷卻＋（Phase 3）Edge Function 或 Cloudflare 版本加強。若未來灌水成災，切換 4.7 的升級路徑。

4.3 前端 API（維持零依賴，直接 fetch）

const SB_URL = 'https://<專案ref>.supabase.co';
const SB_KEY = '<anon public key>';   // 公開常數，非機密
const HDR = { apikey: SB_KEY, Authorization: 'Bearer ' + SB_KEY,
              'Content-Type': 'application/json' };

async function fetchComments(level) {
  const u = SB_URL + '/rest/v1/tower_comments?select=*'
          + '&level=eq.' + level
          + '&order=likes.desc,created_at.desc&limit=50';
  const r = await fetch(u, { headers: HDR });           // 瀏覽器原生 fetch
  if (!r.ok) throw new Error('HTTP ' + r.status);
  return r.json();
}

async function postComment(level, name, text) {
  const r = await fetch(SB_URL + '/rest/v1/tower_comments', {
    method: 'POST', headers: HDR,
    body: JSON.stringify({ level, name, text })
  });
  if (!r.ok) throw new Error('HTTP ' + r.status);
}
  • 所有呼叫以 try/catch＋逾時（約 8 秒）包裝，失敗一律靜默降級到快取，不得影響遊戲本體。
  • 單檔離線版（file://）同樣可用；Supabase REST 預設允許跨來源。

create table tower_comments (
  id         bigint generated always as identity primary key,
  level      int    not null check (level between 1 and 2000),
  name       text   not null check (char_length(btrim(name)) between 1 and 12),
  text       text   not null check (char_length(btrim(text)) between 1 and 30),
  created_at timestamptz not null default now(),
  likes      int    not null default 0,
  reports    int    not null default 0
);
create index idx_tc_level on tower_comments (level, likes desc, created_at desc);

alter table tower_comments enable row level security;
create policy "任何人可讀" on tower_comments for select using (true);
create policy "任何人可新增（受限欄位）" on tower_comments for insert
  with check (likes = 0 and reports = 0);
