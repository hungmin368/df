🐉 龍塔關卡攻略留言 — 實現做法評估報告

日期：2026-10-13 ｜ Task ID：dragon-tower-comments ｜ 範圍：僅評估與設計，不含實作 ｜ 適用版本：v1.9.14（工作區）
結論（TL;DR）：龍塔每一關都是固定且唯一解的預生成盤面，玩家間共用同一張圖，攻略留言非常有價值。但本遊戲目前是純離線靜態網頁（全站無任何網路請求），要讓「其他玩家」看到彼此留言，必須引入一個外部共用儲存。建議採用 Supabase 免費層（Postgres + REST API，前端直接 fetch，不需 SDK、維持零依賴）＋ localStorage 快取離線降級；UI 以「結果畫面留言面板」＋「龍塔遊戲中攻略按鈕」兩個入口呈現（龍塔不計時，看攻略零懲罰）。備選方案為 Cloudflare Workers + D1（更耐灌水、不閒置暫停，但需寫少量後端）。建議分三階段實施：先做 UI 本地模擬驗證體驗，再接雲端，最後加讚／檢舉。
【2026-10-13 定案更新】顯示方式改採 Bilibili 式彈幕：僅頂／底條帶、單向飄過、可開關、短句（30 字），後端仍為 Supabase 首選；設計細節見第八節，完整實施事項與人機分工見第九節。

一、現況分析

項目現況對留言功能的影響
龍塔盤面 js/tower.js 預生成 2000 關（6×6=1-10 … 13×13=1201-2000），每筆為 base36 regionOf 字串，皆唯一解、不旋轉不鏡像。 正面：所有玩家在第 N 關看到完全相同的盤面，「這關先 ✕ 掉四個角」這類攻略才有意義；留言可以精準錨定在 level 1~2000。
進度模型 TOWER={level,max}（main.js:473），最高通關層存 localStorage dinodoku-tower；不可跳關，只能挑 max+1 或重試已通關層。 留言按關號儲存即可；重試同關時留言面板可再次開啟。
遊戲規則 龍塔不計時、不計分（main.js:1343,1357），隱藏提示按鈕（main.js:2281）。 關鍵設計紅利：龍塔遊戲中看攻略留言完全沒有懲罰，可以在盤面上直接放「💬 攻略」按鈕；一般地圖關卡有計時，則不提供此入口。
結果畫面 過關／失敗皆走 #ov-result，龍塔模式由 resTowerUI()（main.js:2412）精簡為「下一關／重新挑戰＋回地圖」。 留言面板最自然的掛載點：失敗（止步第 N 關）時最需要攻略。
網路能力 全 js/ 目錄無任何 fetch／XMLHttpRequest／WebSocket。 需從零引入外部服務；所有留言方案都必須處理「離線／請求失敗」降級。
部署環境 GitHub Pages 靜態託管（https://hungmin368.github.io/df/），另有單檔離線版 dragonfinder_v<ver>.html。 無後端、無法跑 server code；HTTPS 靜態頁呼叫外部 HTTPS API 無 CORS 障礙（多數 BaaS 允許所有來源）；單檔 file:// 開啟時 fetch 到 HTTPS 也可用。
打包腳本 build_single_file.mjs 以固定清單內嵌 data.js／tower.js／main.js，並檢查不得殘留外部引用。 若新增 js/ 檔，必須同步修改打包腳本；或將留言程式碼直接放進 main.js（現有檔案已 3157 行，建議獨立成檔＋改腳本）。
既有慣例 存檔鍵一律 dinodoku-*；工程模式有「清存檔」會逐一移除已知鍵（main.js:945）；UI 全繁體中文。 留言快取鍵應命名 dinodoku-twcomments-* 並加入清存檔清單；留言面板沿用現有 overlay/modal 風格。

二、需求定義

功能需求

  • 每一關（1~2000）有獨立留言串；玩家可讀取、可發表。
  • 留言內容：暱稱（1~12 字，記住上次輸入）＋ 內容（1~200 字），免註冊、免登入。
  • 顯示排序：熱門（讚數）優先、同分再看新；預設顯示最新 50 則。
  • 留言需標注樓層關卡名（例：「龍塔第 137 關（10×10）」）。

非功能需求

  • 離線降級：抓不到雲端時顯示 localStorage 快取並標注「離線快取」；送出失敗提示保留草稿。
  • 故障隔離：留言服務整個掛掉，遊戲本體任何功能都不得受影響（所有請求包在 try/catch，有逾時）。
  • 防灌水基本款：長度限制、同關冷卻（60 秒）、單日上限（如 10 則）、前端敏感詞過濾、檢舉機制。
  • 零成本優先：不綁信用卡、不影響 GitHub Pages 免費託管。
  • 風格一致：沿用現有暖色羊皮紙 modal 風格與繁體中文文案。

三、候選方案比較

方案真實跨玩家共用成本／綁卡穩定性風險防灌水能力實作複雜度綜合建議
A. 純 localStorage 本地留言 否 只有自己 免費、零服務 無 不需（本地） 極低 僅作 Phase 1 過渡＋離線快取層
B. Supabase（Postgres + REST） ⭐建議 是 免費層充足（500MB DB／5 萬 MAU），不綁卡 閒置 7 天暫停，暫停後需上手動恢復；有玩家流量即不會暫停 中：RLS 限制欄位／長度；讚需另設計 低：直接 fetch REST，無 SDK 首選
C. Cloudflare Workers + D1 是 免費層（約 10 萬請求／天、D1 5GB），不綁卡 高：無閒置暫停 強：可自寫 IP 頻率限制、過濾、長度 中：要寫 worker（JS 後端）並用 wrangler 部署 備選／長期升級
D. Firebase Firestore 是 Spark 免費（讀 5 萬／天、寫 2 萬／天）；2024/10 後新專案部分服務需綁 Cloud Billing（額度內仍 $0） 高 中：安全規則可限長度欄位 中低：REST 亦可用，但官方主推 SDK（違背零依賴精神） 可行但非首選
E. Google Apps Script + 試算表 是 完全免費、不綁卡 低~中：延遲高、每日／每分鐘配額、併發寫入偶爾失敗 弱：全靠自寫腳本 低：doGet/doPost + fetch 過渡可行，長期不建議
F. giscus（GitHub Discussions） 是（留言者需登入 GitHub） 完全免費、零維運 高 最強：GitHub 帳號門檻擋掉幾乎所有垃圾 低~中：嵌入現成 widget 不符客群：手機休閒玩家多無 GitHub 帳號；2000 關＝2000 個 discussion 難管理
（不予採納）第三方免費 JSON 存儲（jsonbin 等） 是 免費 服務存續風險高、配額小 弱：金鑰放前端即形同公開 低 不建議正式使用

※ 免費額度為 2026-10 當下查證結果，導入前請以各官網為準。Supabase「7 天低活動暫停、來源請求可防止暫停、暫停後需手動恢復」已查證官方文件；Firebase Spark 免費額度（Firestore 讀 5 萬／天、寫 2 萬／天）已查證。

四、建議方案細部設計（Supabase）

4.1 資料表結構

create table tower_comments (
  id         bigint generated always as identity primary key,
  level      int    not null check (level between 1 and 2000),
  name       text   not null check (char_length(btrim(name)) between 1 and 12),
  text       text   not null check (char_length(btrim(text)) between 1 and 200),
  created_at timestamptz not null default now(),
  likes      int    not null default 0,
  reports    int    not null default 0
);
create index idx_tc_level on tower_comments (level, likes desc, created_at desc);

單表即可；2000 關以索引查詢毫無壓力。留言量極大時（數萬則以上）再考慮分頁（Range header）。

4.2 安全規則（Row Level Security）

alter table tower_comments enable row level security;

create policy "任何人可讀"  on tower_comments for select using (true);
create policy "任何人可新增（受限欄位）" on tower_comments for insert
  with check (likes = 0 and reports = 0);
-- 故意「不」建立 update／delete 政策：匿名金鑰無法改刪任何留言

誠實的限制：Supabase 的 anon 金鑰會出現在前端原始碼，這是公開常數而非機密；RLS 能保證的是「只能新增合法長度的資料、不能改刪」，防灌水主要仍靠前端冷卻＋（Phase 3）Edge Function 或 Cloudflare 版本加強。若未來灌水成災，切換 4.7 的升級路徑。

4.3 前端 API（維持零依賴，直接 fetch）

const SB_URL = 'https://<專案ref>.supabase.co';
const SB_KEY = '<anon public key>';   // 公開常數，非機密
const HDR = { apikey: SB_KEY, Authorization: 'Bearer ' + SB_KEY,
              'Content-Type': 'application/json' };

async function fetchComments(level) {
  const u = SB_URL + '/rest/v1/tower_comments?select=*'
          + '&level=eq.' + level
          + '&order=likes.desc,created_at.desc&limit=50';
  const r = await fetch(u, { headers: HDR });           // 瀏覽器原生 fetch
  if (!r.ok) throw new Error('HTTP ' + r.status);
  return r.json();
}

async function postComment(level, name, text) {
  const r = await fetch(SB_URL + '/rest/v1/tower_comments', {
    method: 'POST', headers: HDR,
    body: JSON.stringify({ level, name, text })
  });
  if (!r.ok) throw new Error('HTTP ' + r.status);
}
  • 所有呼叫以 try/catch＋逾時（約 8 秒）包裝，失敗一律靜默降級到快取，不得影響遊戲本體。
  • 單檔離線版（file://）同樣可用；Supabase REST 預設允許跨來源。

4.5 離線與快取策略

  • 每次成功讀取，把該關留言存入 localStorage dinodoku-twcomments-<level>（含時間戳）；最近看過的 20 關為上限，避免爆量。
  • 讀取失敗／離線 → 改顯示快取，面板頂部標注「📡 離線中，顯示快取留言（更新於 xx）」。
  • 送出失敗 → 保留輸入內容並提示「網路不穩，稍後再試」，不清空草稿。
  • 快取鍵加入工程模式「清存檔」清單（main.js:945）。

4.6 防灌水與內容安全（第一版）

  • 長度：資料庫 check 硬限制（暱稱 12、內容 200 字）。
  • 頻率：同一關 60 秒冷卻；單一裝置（localStorage 計數）單日上限 10 則。
  • 敏感詞：前端內建小黑名單過濾（命中即阻擋送出）。
  • 檢舉：每則留言「⚠ 檢舉」→ 寫入 reports+1（Phase 2）；後台以 Supabase Dashboard 手動巡查，滿 3 檢舉可人工刪除（Dashboard 直接操作）。
  • 免責：面板底部一行「留言由玩家提供，與本遊戲立場無關」。

4.7 整合注意與升級路徑

  • 新增 js/tower_comments.js（建議獨立檔）：index.html 以 <script src="js/tower_comments.js?v=x"> 引入（main.js 之前）；build_single_file.mjs 需同步加入內嵌規則與 sanity check。
  • 存檔／版本慣例：所有新鍵用 dinodoku- 前綴；版本參數 ?v= 跟隨當次發布版本。
  • 升級路徑：若免費層不敷使用或灌水嚴重 → 在 Supabase 前加 Edge Function（服務端頻率限制＋Cloudflare Turnstile 驗證），或整體遷至方案 C（Cloudflare Workers + D1）。兩者前端都仍是單一 fetch endpoint，切換成本低（只需換 URL 與欄位對映）。
  • 資料可攜：Supabase 隨時可匯出全表 CSV/SQL，無鎖定風險。

八、彈幕模式設計（2026-10-13 定案）

本節為最新定案：顯示層採 Bilibili 式彈幕，取代 4.4 的留言面板（長文面板可作為未來選配並存）。後端儲存與安全設計（第四節 schema／RLS／防灌水）全部沿用，僅字數上限調整。

設計項目定案內容
顯示位置僅兩條帶：頂帶（HUD 下方、盤面上緣）與底帶（controls 上緣）。盤面永不被遮擋——這是解謎遊戲採用彈幕的前提。
方向與生命週期單向右→左；飄出畫面即從 DOM 移除（即播即毀，不循環堆積）。
軌道與同屏上限每帶 2 軌（手機每帶 1~2 軌），同屏上限 6~8 條；超出的留言進佇列依序播出，避免疊彈。
速度與節奏每條約 10 秒橫越；進關先播快取留言，雲端載入完成後接續；冷門關（0 留言）顯示本地引導句「還沒有攻略彈幕，搶頭香！」（非假資料）。
字數彈幕短句 30 字上限（schema 的 text check 由 200 改為 30；未來若加長文面板再擴充欄位）。
開關「💬」按鈕即時開關，記憶於 localStorage dinodoku-danmaku-on；龍塔預設開（不計時零懲罰）、一般計時關卡預設關。
輸入入口龍塔遊戲中 controls 一顆「💬」展開小輸入列（暱稱＋30 字）；送出後自己的彈幕立即右→左飄出（樂觀播放，不等伺服器回應寫入成功才顯示，失敗則提示保留草稿）。結果畫面同入口。
資料流同一張 tower_comments 表；進關時 GET?level=eq.N&limit=20 → 播放佇列；快取 dinodoku-twcomments-<level>；離線／服務暫停時播快取並顯示「📡」提示。
防灌水沿用：60 秒同關冷卻、單日 10 則、敏感詞黑名單、RLS（匿名僅可新增、不可改刪）。
效能純 CSS transform 動畫（GPU 合成、不觸發 layout）；無新增第三方依賴。

第 4 項的建表 SQL（貼進 Supabase SQL Editor 執行）

create table tower_comments (
  id         bigint generated always as identity primary key,
  level      int    not null check (level between 1 and 2000),
  name       text   not null check (char_length(btrim(name)) between 1 and 12),
  text       text   not null check (char_length(btrim(text)) between 1 and 30),
  created_at timestamptz not null default now(),
  likes      int    not null default 0,
  reports    int    not null default 0
);
create index idx_tc_level on tower_comments (level, likes desc, created_at desc);

alter table tower_comments enable row level security;
create policy "任何人可讀" on tower_comments for select using (true);
create policy "任何人可新增（受限欄位）" on tower_comments for insert
  with check (likes = 0 and reports = 0);

與 4.1 節差異：彈幕定案後 text 上限 200 → 30。未來若加長文面板，放寬此 check 即可（alter table ... drop constraint + 重建）。
